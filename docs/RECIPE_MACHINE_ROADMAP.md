# Recipe-Machine Roadmap (S-MACHINES Stage 4+) — to a real recipe-processing Enrichment Chamber on Fabric

From the `s-machines-recipe-roadmap` workflow (5 scouts/designer/3 verifiers; all sound-with-fixes; Stage 1 empirically compiled green by a verifier).

## Overview
Roadmap from the just-landed TileEntityMekanismBase split (HEAD 84b77e49e9, all three targets green, Fabric 11/11 self-tests pass) to a headless real-recipe Enrichment Chamber ticking on Fabric using Mekanism's actual recipe-cache engine (not the FabricRealMachines demo loop). I verified every scout claim against source. The path drains leaves-first: recipe-cache item leaves -> the OneInput/helper fluid-split -> the MekanismRecipeType IRecipeWorldAccess seam (the single deepest blocker, gating both the lookup layer and the whole prefab chain) -> the inventory-slot/energy-slot resolution -> the ISideConfiguration/TileComponentConfig stub-or-seam (the hardest coupling) -> prefab-chain re-parent -> the chamber itself + Fabric BE-type/cap registration. One scout assumption needs correcting: the recipe-cache 'class-split leaving fluid factories on neoforge' is NOT free — see Stage 2 risk. The first stage I detail is the strictly byte-identical pure-hoist subset, the highest value-per-risk safe cut.

## Total scope (honest)
Honest size: ~7 stages, roughly 10-14 focused sessions, before a headless real-recipe Enrichment Chamber ticks on Fabric. File count touched/moved is moderate (~40-60 files across all stages), but the cost is concentrated in three deep seams, not in volume: (a) the MekanismRecipeType IRecipeWorldAccess service-seam + base-split (the keystone — gates the recipe-cache LOOKUP layer AND every prefab class above TileEntityRecipeMachine, because IRecipeLookupHandler -> IMekanismRecipeTypeProvider names the concrete MekanismRecipeType); (b) the ISideConfiguration / TileComponentConfig coupling (TileComponentConfig imports net.neoforged BlockCapability and is irreducibly welded to ContainerType — it CANNOT move to :common; the chamber ctor hard-calls configComponent.setupItemIOConfig + setupInputConfig(ENERGY), so this stage must STUB the side-config behind an overridable hook or accept fixed-slot I/O — this is the single hardest wall and the largest source of schedule uncertainty); (c) EnergyInventorySlot, welded to MekanismRecipeType.ENERGY_CONVERSION + EnergyCompatUtils, which for the first chamber should be stubbed/omitted (pre-fill MachineEnergyContainer) rather than ported. Reality check the scouts confirmed and I re-verified: the existing Fabric demo ALREADY does real vanilla-datapack recipe DATA lookup via serverLevel.recipeAccess().getRecipeFor(ENRICHING,...) and proves dirt->diamond end-to-end; the remaining gap to a 'real machine' is the Mekanism recipe-CACHE engine (CachedRecipe / RecipeCacheLookupMonitor / OneInputCachedRecipe pipeline + MekanismRecipeType.findFirstRecipe input-cache) plus config-driven I/O, NOT recipe data access. Do not conflate the two and declare victory ~3 stages early. Byte-identity holds cleanly for Stages 1, 3, 5, 7; Stages 2 (recipe-cache fluid-split) and 4 (recipe-type seam) carry real NeoForge risk that this environment cannot validate and MUST be flagged for the user's in-game test. The GUI/menu (real Mekanism container + SyncMapper) is explicitly OUT of scope for the headless milestone and is a separate large effort after it.

## Risks
- STAGE 2 IS NOT A FREE BYTE-IDENTICAL SPLIT (scout S2/S5 understated this — I verified): OneInputCachedRecipe's chemical factories (crystallizing/itemToChemical/chemicalToChemical/sawing) use ConstantPredicates.CHEMICAL_EMPTY and fluid factories use FLUID_EMPTY/INVALID_FLUID_TEMPLATE — all neoforge-ONLY constants, not just the FluidStack TYPES. A renamed residue companion changes the invokestatic owner in ~20 chemical/fluid tiles (EvaporationMultiblockData, every Chemical* tile, sawmill/electrolytic factories — enumerated) => NOT byte-identical, forces in-game retest of nearly all machines. The byte-identical alternative is an IFluidStack/IFluidStackTemplate-templated signature so the class hoists at one FQN — more work. This decision must be made explicitly in Stage 2, not assumed away.
- SEQUENCING TRAP (the Stage-3 verifier's exact warning): the prefab chain shows 0 net.neoforged imports on every file (I confirmed all 4 + the chamber), but is transitively welded to MekanismRecipeType via IRecipeLookupHandler -> IMekanismRecipeTypeProvider (names concrete MekanismRecipeType, verified line refs). Anyone attempting a loader-neutral prefab base BEFORE Stage 4 lands hits an uncompilable :common move. Zero loader imports does NOT mean compiles in :common.
- THE HARD WALL (Stage 6): TileComponentConfig imports net.neoforged BlockCapability and is irreducibly welded to ContainerType — it CANNOT move to :common, yet the chamber ctor hard-calls configComponent.setupItemIOConfig + setupInputConfig(ENERGY) (TileEntityElectricMachine lines 66-67). The first chamber MUST stub the side-config behind an overridable hook or accept fixed-slot I/O. This is the single largest schedule risk; if the interface-narrow proves deeper than a hook, Stage 6 may itself split into two.
- STAGE 4 RUNTIME RISK THE COMPILE GATE WON'T CATCH: the IRecipeWorldAccess seam changes how the recipe map resolves client-vs-server. The Fabric impl returns null client-side until the GUI stage; if findFirstRecipe is ever called client-side before then it NPEs at tick time. And NeoForge byte-identity rests on the verbatim-moved-logic argument plus the vanilla-smelting-wrap mirror — MUST be flagged for the user's in-game NeoForge recipe-lookup test (both client and server) before merge.
- ENERGY-SLOT DEFERRAL: EnergyInventorySlot is welded to MekanismRecipeType.ENERGY_CONVERSION + EnergyCompatUtils (6 sites) + ItemStackToEnergyRecipe. The headless chamber MUST pre-fill MachineEnergyContainer and omit the charge slot (fillOrConvert), else the chamber won't compile in :common. A real charge slot is a separate post-milestone stage needing an EnergyCompatUtils energy-item-cap service-seam over api IStrictEnergyHandler.
- DON'T DECLARE VICTORY EARLY: the existing Fabric demo already does real getRecipeFor(ENRICHING,...) datapack lookup and proves dirt->diamond — that is recipe DATA access, already done. The milestone is the recipe-CACHE engine (CachedRecipe pipeline + MekanismRecipeType.findFirstRecipe input-cache) + config-driven I/O on top of it. Conflating the two would claim done ~3 stages prematurely.
- addContainerTrackers(MekanismContainer) is overridden at three prefab levels; any sync hook in Stage 6 must preserve exact super-call order or GUI property indices desync, and on NeoForge must stay byte-identical — keep it leaf-resident behind a no-op common tracker hook, do not attempt to hoist it.
