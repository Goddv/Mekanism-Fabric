## IFluidStack interface
PLACE: common/src/main/java/mekanism/api/fluid/IFluidStack.java (loader-neutral, compiles against vanilla MC only). This is a stack-shaped abstraction (NOT a registry-provider service): it bundles a fluid type + amount + components, exactly mirroring how common/.../chemical/ChemicalStack.java is a single concrete class. The KEY DESIGN DECISION the layer maps got wrong: in transfer-api v8.0.5 (the MC 26.1 build, jar net.fabricmc.fabric-api:fabric-transfer-api-v1:8.0.5+357ea7334c) FluidVariant is NOT a foreign component model. javap shows `FluidVariant extends TransferVariant<Fluid>` where TransferVariant `extends net.minecraft.core.component.DataComponentHolder` and exposes `getComponentsPatch():DataComponentPatch`, `getComponents():DataComponentMap`, `typeHolder():Holder<Fluid>`, `getFluid():Fluid`, `isBlank()`, `isOf(O)`, `componentsMatch(DataComponentPatch)`, `of(Fluid)`, `of(Fluid,DataComponentPatch)`, `withComponents(DataComponentPatch)`, plus `FluidVariant.CODEC` and `FluidVariant.PACKET_CODEC` (a StreamCodec). NeoForge FluidStack is also Fluid+amount+DataComponentPatch. So BOTH loaders speak vanilla DataComponentPatch — the components model is shared, not split, which collapses the layer maps' HIGH "DataComponentPatch vs ComponentChanges" blocker.

MINIMAL SURFACE (derived from actual usage in IExtendedFluidTank/IMekanismFluidHandler/ISidedFluidHandler/ExtendedFluidHandlerUtils/BasicFluidTank — every method below is backed by a real call site):

DELIBERATELY EXCLUDED from the minimal interface (defer): grow(long)/shrink(long)/setAmount(long) as in-place mutators. The layer maps flag ExtendedFluidHandlerUtils.extract lines 151/203/249/304 calling extracted.grow(...) on a mutable FluidStack. Resolve that during the handler-hoist slice by rewriting `extracted.grow(drained.amount())` to `extracted = extracted.copyWithAmount(extracted.getAmount()+drained.getAmount())` (immutable, works on both loaders) rather than baking mutability into IFluidStack — Fabric FluidVariant is immutable. Mutation stays an impl detail INSIDE tank classes (BasicFluidTank.stored), not on the shared stack contract.

## Fabric impl
PLACE: fabric/src/main/java/mekanism/fabric/fluid/FabricFluidStack.java (final class) implementing IFluidStack by wrapping TWO fields: a net.fabricmc.fabric.api.transfer.v1.fluid.FluidVariant variant + a long amount (in droplets; FluidConstants.BUCKET droplets per bucket). This is the exact ChemicalStack(Holder+long) shape, except the holder+components live inside FluidVariant. Methods:
  typeHolder() -> variant.typeHolder() (transfer-api provides it); getFluid() -> variant.getFluid(); getAmount() -> isEmpty()?0:amount; isEmpty() -> variant.isBlank() || amount<=0; getComponentsPatch() -> variant.getComponentsPatch() (vanilla DataComponentPatch — no translation needed); getHoverName() -> FluidVariantRendering/Fluid description, or simple Component from fluid (client-only render handler avoided server-side; use a plain name on server); is(Holder) -> variant.getFluid()==holder.value() (or holder.is); is(TagKey) -> variant.getFluid().builtInRegistryHolder().is(tag); copy() -> new FabricFluidStack(variant, amount) (variant is immutable, share it); copyWithAmount(long n) -> n<=0?empty():new FabricFluidStack(variant, n) (NO new variant alloc — variant unchanged, only amount differs; immutability handled by returning a new wrapper).
AMOUNT — THE OUT-OF-VARIANT PROBLEM, SOLVED: amount is a sibling long stored ON the wrapper (FluidVariant has none), identical to how ChemicalStack stores its own long beside Holder<Chemical>. Internal API unit choice: keep droplets internally on Fabric. mB<->droplet conversion (×FluidConstants.BUCKET/1000 = ×81 on write to a Fabric Storage, ÷81 clamp on read) happens ONLY at the fabric-transfer Storage boundary in a future tank-bridge slice; the IFluidStack/handler layer itself is unit-agnostic (it just moves longs), so the lossy ÷81 risk is confined and deferred — it does NOT affect this slice.
CODECS — the layer maps' hardest blocker, now EASY: javap confirms FluidVariant.CODEC (Codec<FluidVariant>) and FluidVariant.PACKET_CODEC (StreamCodec<RegistryFriendlyByteBuf,FluidVariant>) EXIST in v8.0.5. So FabricFluidStackProvider builds the IFluidStack codec with RecordCodecBuilder grouping FluidVariant.CODEC(fieldOf "id") + a positive-long codec(fieldOf "amount"), and the stream codec via StreamCodec.composite(FluidVariant.PACKET_CODEC, ByteBufCodecs.VAR_LONG). optionalCodec wraps with ExtraCodecs.optionalEmptyMap exactly like ChemicalStack.OPTIONAL_CODEC (lines 66-67). This is a faithful clone of the ChemicalStack codec block (ChemicalStack.java lines 51-132) with FluidVariant substituted for the chemical holder.
SERVICE IMPL: fabric/src/main/java/mekanism/fabric/fluid/FabricFluidStackProvider.java implements IFluidStackProvider; empty()->new FabricFluidStack(FluidVariant.blank(),0); of(holder,amount,patch)->new FabricFluidStack(FluidVariant.of(holder.value(),patch),amount). Wired via fabric/src/main/resources/META-INF/services/mekanism.api.fluid.IFluidStackProvider (mirrors the 3 existing fabric service files).

### fabric-fluidvariant
Fabric's net.fabricmc.fabric.api.transfer.v1.fluid.FluidVariant can back a portable IFluidStack abstraction on Fabric, but with critical architectural mismatches: FluidVariant stores only fluid + components (no amount), requires a separate long (in droplets, 81000/bucket) paired alongside it, and has fundamentally different semantics for data persistence vs. NeoForge's DataComponent-bundled FluidStack. The Fabric type is immutable and copyable but lacks codec/stream-codec pairs—encoding will require custom serialization. Components mapping (NeoForge DataComponentPatch ↔ Fabric ComponentChanges) is the deepest coupling blocker.

### fluidstack-usage-scope
FluidStack is referenced across 180 files (41 API + 120 impl + 4 common + 0 fabric). The API surface (mekanism.api.fluid.*, mekanism.api.recipes.*) accounts for 41 files: 5 fluid handlers, 27 recipe types + serializers, 2 inventory slots, 1 predicate helper, 5 datagen builders. Core issue: NeoForge FluidStack (Fluid + amount + DataComponents) is tightly coupled to recipes, handlers, and ingredients. Fabric lacks FluidStack entirely—it uses FluidVariant (Fluid + components, no amount) + long droplets. ## SLICE 2 FINDING (handler-API hoist) — architectural wrinkle + cascade scope
Investigated after slice 1. The handler hierarchy HARD-extends NeoForge's fluid capability interfaces:
- `IExtendedFluidHandler extends net.neoforged.neoforge.fluids.capability.IFluidHandler`
- `IExtendedFluidTank extends net.neoforged.neoforge.fluids.IFluidTank` (+ IFluidHandler)
- `ISidedFluidHandler extends IExtendedFluidHandler`; `IMekanismFluidHandler extends ISidedFluidHandler`
So these interfaces ARE the NeoForge fluid capability — used via `Capabilities.FLUID` (FluidUtils.java:105, StorageUtils, LookingAtUtils:137 return/expect `IFluidHandler`).
CASCADE: 53 `neoforge/src/main` files reference the handler API (34 import FluidStack). 12 implement IExtendedFluidTank (BasicFluidTank etc.). The interface signature change (FluidStack→IFluidStack) is ATOMIC — no green intermediate; all 53 + the bridge must change together.
BRIDGE DESIGN for when this is tackled: move `:common` handler interfaces over IFluidStack but DO NOT extend NeoForge IFluidHandler/IFluidTank. NeoForge exposes them as the vanilla/Neo fluid cap via an ADAPTER (wrap IExtendedFluidHandler -> IFluidHandler at the `Capabilities.FLUID` registration boundary — a handful of cap-registration sites, not all 53). ExtendedFluidHandlerUtils: rewrite mutable `extracted.grow(n)` -> `extracted = extracted.copyWithAmount(extracted.getAmount()+n)` (Fabric FluidVariant is immutable). FluidActions stays neoforge permanently. Fabric side: expose via BlockApiLookup (already proven with ISimpleFluidHandler). This is a dedicated multi-step effort; slice-1 foundation (IFluidStack + both impls + capability) is done + de-risks it.
