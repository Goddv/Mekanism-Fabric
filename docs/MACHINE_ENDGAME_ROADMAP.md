# Machine Endgame Roadmap (S-MACHINES)

From the `s-machines-roadmap` workflow (6 scouts → designer → 3 adversarial verifiers, all `sound-with-fixes`). Verified against the live tree, not the stale docs.

## Overview
Re-baselined against ground truth (not the stale docs): the capability/sync/config/fluid seams are ALREADY built and live on both loaders; TileEntityMekanism (1617 lines) has ZERO net.neoforged imports; the prefab chain (Enrichment/Electric/Progress/Recipe/Configurable) and MachineEnergyContainer are net.neoforged-clean; the BlockType<->tile back-edges are already cut at the type level via ITileHolder + IHasTileEntity. So the endgame is mostly intra-mekanism hoist-ordering plus FOUR genuine remaining seams. The four real walls inside the tile core: (1) CLIENT-ONLY-VANILLA sound coupling — TileEntityMekanism declares `private SoundInstance activeSound` (line 254) and imports net.minecraft.client.Minecraft (118) + net.minecraft.client.resources.sounds.SoundInstance (119) and calls SoundHandler (6 net.neoforged) statics in updateSound() (lines 1497-1532); on Fabric's SPLIT distribution net.minecraft.client.* is absent from the dedicated-server classpath, so this blocks the hoist independently of net.neoforged — the hidden-coupling trap the repo notes warn about; (2) ContainerType.TYPES static iteration driving 6 save/load/data-component methods, net.neoforged-capability-bound (ItemCapability/ItemAccess/DeferredHolder); (3) MekanismRecipeType client/server world-access (FMLEnvironment/ServerLifecycleHooks/MekanismClient) gating the recipe engine; (4) SyncMapper neoforgespi annotation scan gating dynamic container sync. The cycle itself only needs ContainerTypeRegistryObject narrowed to a :common IContainerProvider interface (one cut, used at BlockTypeTile.withGui + AttributeGui + Factory). Recommendation (matches scout S6): do NOT attempt a full functional machine in one push. Stage 1 is the smallest byte-identical safe cut that drains the highest hidden risk: extract the client-only sound logic behind an ITileSoundService seam (exact shape of the proven ITileSyncService), removing net.minecraft.client.* + SoundHandler from the tile body so it becomes server-classpath-clean on a split distribution. Byte-identical on NeoForge (pure indirection through a singleton); precondition for every later tile-core hoist to even compile on Fabric.

## Total scope (honest)
Brutally honest: largest remaining effort in the port — a multi-session campaign, not a sprint. Verified: common/src/main ~425 files; neoforge/src/main ~1523 (~1089, ~71%, are net.neoforged-clean, blocked only by intra-mekanism order). Full-machine core closure is ~381 loader-clean files + ~169 seam boundaries, but the FIRST machine does not need all of it. Realistic move-set to a first FUNCTIONAL Enrichment Chamber on both loaders is ~80-110 files (tile core + component cluster + recipe-cache + container/sync + 5 prefab tiles + per-loader registration/GUI) plus 4 new seams (sound, recipe-world-access, sync-mapper, container-provider). Estimate 8 stages / ~8-12 focused sessions. Stages 1-3 (sound seam, recipe-cache hoist, tile-core hoist as energy-only) are byte-identical-on-NeoForge and autonomously safe. Stages 4-8 increasingly need the user's in-game NeoForge regression test (registration/runtime). A real ENERGY-ONLY tile on both loaders is achievable in 3 stages; real RECIPE PROCESSING in ~5; the full GUI machine retiring the Fabric demo in ~8. Promise the energy-tile slice first, then recipe, then GUI — not the full machine near-term.

## Cycle-break strategy
The cycle is ALREADY severed at the type level (verified): BlockTypeTile holds Supplier<ITileHolder<TILE>> (a :common interface) not TileEntityTypeRegistryObject; getTileType() returns ITileHolder; the tile->blocktype back-edge goes through IHasTileEntity.getTileType():ITileHolder (both :common). The ONLY remaining compile edge blocking BlockType/BlockTypeTile/Machine/AttributeGui from :common is ContainerTypeRegistryObject, referenced at exactly 3 places: BlockTypeTile.withGui (lines 49/53), AttributeGui (field + ctor + getProvider calling getProvider(Component,Object,boolean):MenuProvider), and Factory. EXACT cut sequence (Stage 8, AFTER tile core + container stack are hoisted): (a) Introduce :common interface IContainerProvider { @Nullable MenuProvider getProvider(Component name, Object tile, boolean resetMousePosition); } (MenuProvider/Component are :common-safe). (b) Make NeoForge ContainerTypeRegistryObject `implements IContainerProvider` ADDITIVELY — keep every existing getProvider overload byte-identical so AttributeGui's call site (already getProvider(Component,Object,boolean)) is unchanged at bytecode level. (c) Retype BlockTypeTile.withGui + AttributeGui field/param from Supplier<ContainerTypeRegistryObject<...>> to Supplier<? extends IContainerProvider>. (d) Now BlockType/BlockTypeTile/Machine (base) + AttributeGui + AttributeSound (SoundEventRegistryObject already :common) import only :common/vanilla/api types -> same-FQN git mv to :common. (e) Keep Machine.FactoryMachine + AttributeUpgradeable->MekanismBlocks.getFactory on NeoForge (deferred supplier but a compile import); hoist only base Machine + a pure createMachine() path; the FactoryType tier system stays per-loader to avoid the FactoryType->MekanismBlockTypes closure explosion. (f) The registry monoliths (MekanismBlockTypes/Blocks/TileEntityTypes/ContainerTypes) stay per-loader as declaration boundaries — all-or-nothing per FILE (each imports ~60 concrete tiles); Fabric registers the chamber via a parallel :common composition-stack mirror referencing now-common content classes, NeoForge keeps its monolith byte-identical.

## NeoForge identity argument
Stage 1 is byte-identical-equivalent on NeoForge by construction. The change is pure indirection: the exact statements of updateSound() (SoundHandler.start/stopTileSound, the Minecraft.getInstance().getSoundManager().isActive() check, the SoundInstance token) move VERBATIM, same order, into NeoTileSoundService, and the tile calls them through the ITileSoundService.INSTANCE singleton — the identical pattern already shipped/accepted for ITileSyncService/IContainerSyncSender/ICapabilityExposureService. The field retype SoundInstance->Object is invisible at the call sites (the token only flows back into the impl which casts it back). The only runtime delta is one extra virtual dispatch through MekanismAPIBase.getService — the established accepted cost of the seam pattern, not a behavioral change. No registration, NBT, packet, or recipe surface is touched, so save-compat and wire-compat are unaffected. General discipline for later stages: same-FQN git mv (no body change) is byte-identical for files NeoForge still compiles; base-splits keep the NeoForge side on inherited dispatch with unchanged signatures; any stage touching registration (7,8) or runtime menu/sync (7) is flagged high-needs-ingame-test because NeoForge runtime cannot be validated here, per the mandate. Hard rule preserved throughout: nothing in :common imports net.neoforged/net.fabricmc/dev.architectury, and after Stage 1 nothing in the tile body imports net.minecraft.client.* (the split-distribution server-classpath constraint the docs missed).


## Risks
- HIGHEST-RISK ASSUMPTION (do NOT do this): bundling the full functional machine into one stage crosses the sound seam + ContainerType.TYPES save/load + MekanismRecipeType world-access + container/sync + the BlockType cycle cut simultaneously — five independent risk sources — impossible to keep per-stage-green or per-stage-byte-identical. The roadmap isolates each into its own stage.
- The SCOUTS UNDER-WEIGHTED the client-only-vanilla coupling: TileEntityMekanism declaring `private SoundInstance activeSound` + importing net.minecraft.client.Minecraft means the tile body is NOT hoistable to :common today even with zero net.neoforged imports — on Fabric's SPLIT distribution net.minecraft.client.* is absent from the dedicated-server classpath. This is the repo's HIDDEN-COUPLING trap; only the Fabric compile gate would catch it. Stage 1 exists to drain this before any tile-core hoist; skipping it makes Stage 3 fail to compile on Fabric confusingly.
- ContainerType.TYPES static iteration (loadAdditional/saveAdditional/applyImplicitComponents/collectImplicitComponents/getRemapEntries + ctor getListener) is the deepest save/load blocker and is net.neoforged-capability-native (ItemCapability/ItemAccess/DeferredHolder). Stage 3 must keep these on the NeoForge residue (or behind an IContainerTypeRegistry seam); hoisting them into :common would drag the capability machinery in and break the no-neoforged-in-common rule. A real constraint on how clean the Stage-3 hoist can be.
- MekanismRecipeType's FMLEnvironment/ServerLifecycleHooks/MekanismClient client/server world-access (lines 199-214) is the single genuinely-NEW seam still required for recipe processing; underestimating it stalls Stages 4-5. Its smelting vanilla-recipe wrap (255-267) must be mirrored on Fabric or smelting recipes diverge between loaders.
- NeoForge runtime regression cannot be validated in this environment. Stages 1-3 are byte-identical/seam-only and autonomously safe; Stages 7-8 (container/sync, GUI, registration cycle cut) touch runtime menu-open + registration and MUST land with the user's in-game NeoForge test (per AUTONOMOUS_SESSION_STATUS.md / the registry-timing rule). Do not merge a registration-touching stage without that test.
- Sync packet-format parity: when Stage 7 lands the real MekanismContainer/Syncable* path, the Fabric IContainerSyncSender wire format must match NeoForge exactly or the GUI energy-bar/progress-arrow desyncs — the demo sidesteps this with vanilla ContainerData, so it is net-new unproven risk on Fabric.
- FactoryType->MekanismBlockTypes is the documented closure-explosion edge: any stage pulling FactoryMachine/AttributeFactoryType into the move-set detonates the 381-file closure into one commit. The plan keeps the FactoryMachine tier system + registry hubs per-loader as boundaries; the chamber is registered today via createFactoryMachine, so the first real-machine stage must use a pure-createMachine target or explicitly scope out the factory variant.
